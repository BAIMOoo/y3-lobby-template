# 问题硬化流程

仅在 `SKILL.md` 的“硬化信号”出现时读取本文件。目标是把可推广的真实故障转成可执行的回归保护，
而不是积累故障笔记。

## 1. 保护现场

先查看 Skill 目录的 Git 状态，识别本轮开始前已经存在的修改。保留用户修改；新修复围绕它们工作。

完成标准：能够区分原有修改、本轮故障输入、本轮将要修改的文件。

## 2. 捕获证据

保留能够独立重现问题的最小材料：原始 DSL 或调用、实际输出或错误、期望结果和期望结果的来源。
编辑器行为以编辑器重新保存的脱敏 JSON 为证据；ECA 名称和参数以当前索引或项目定义为证据。

完成标准：不依赖当前对话，仅使用保存的输入和命令即可重现问题。

## 3. 判断是否推广

同时满足以下条件时，才修改通用 Skill：

- 问题可稳定复现。
- 问题可能影响其他地图或其他同类 ECA。
- 预期行为有索引、项目定义、编辑器样本或用户明确约束作为判据。

不满足时，在当前项目内解决并说明未推广原因；不要向 Skill 添加猜测、一次性 workaround 或业务数据。

## 4. 建立红色回归

先选择最窄的可执行保护：

| 故障 | 回归位置 |
|---|---|
| 参数构建和纯 JSON 转换 | `tests/regressions/*.json`；当前支持 `build_arg` 案例 |
| 生成器、索引或变量管理逻辑 | 对应的 `tests/test_*.py` 单元测试 |
| 校验器漏报 | `tests/test_trigger_validator_hardening.py` 中的非法输入测试 |
| 编辑器序列化差异 | `tests/fixtures/` 的脱敏编辑器样本与整表比对测试 |
| 工作流或工具选择错误 | 可执行检查优先；无法执行时才修改 `SKILL.md` 的步骤或不变量 |

修复代码前运行目标测试并确认它因当前故障失败。若故障在本轮开始前已经被修复，保留能够在旧错误
输出上失败的断言，并在交付说明中标明未观察到红色阶段。

### JSON 回归案例

在 `tests/regressions/` 新增语义化文件名的 JSON。`build_arg` 案例格式：

```json
{
  "id": "stable-case-id",
  "kind": "build_arg",
  "index": {"ECA_NAME": {"p": [], "t": ["TYPE"], "o": []}},
  "value": ["ECA_NAME"],
  "expected_type": "TYPE",
  "assertions": [
    {"pointer": "/arg_type", "equals": 100003}
  ]
}
```

`pointer` 使用 JSON Pointer 语法。一个案例只表达一个故障；复杂行为直接写具名 Python 测试。

完成标准：回归测试能区分故障实现与正确实现，断言不依赖无关字段。

## 5. 修复正确层级

| 事实类型 | 单一事实来源 |
|---|---|
| 可计算的结构规则 | 生成器或校验器代码 |
| 编辑器保存格式 | 脱敏 fixture |
| ECA 名称、参数和返回类型 | 可刷新索引或项目数据 |
| 必须遵循的操作顺序 | `SKILL.md` 工作流 |
| 仅部分分支需要的细节 | 条件引用的参考文件 |

在最低且稳定的层级修复。用代码或测试表达过的规则不再复制到长篇故障说明中。

## 6. 验证和清理

运行：

```powershell
py -3 .codex\skills\eca-json-builder\verify_skill.py
```

涉及编辑器格式时，再执行一次“生成 → 加载 → 编辑器保存 → 关键结构比对”。删除临时输入、测试输出
和未使用的说明；保留最小回归案例及其可靠判据。

完成标准：统一验证成功；编辑器相关改动具有往返证据；Skill 中没有失效指针或重复规则。

## 7. 交付

报告本轮发现、永久修复、增加的回归保护、验证结果，以及未推广的问题及原因。不要把过程历史写成
Skill 内的 changelog。
