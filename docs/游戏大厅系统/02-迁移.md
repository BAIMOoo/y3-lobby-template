# 迁移

[返回文档首页](./README.md)

本章说明如何把大厅服务框架接入目标项目。迁移重点是复制框架文件、配置地图模式和项目 JSON；ECA 项目还需要导入随迁移包提供的触发包。不要照抄测试项目的关卡、模式、匹配规则或玩法逻辑。

仓库的 `main` 分支用于参考 Lua 实现，`eca-example-map` 分支用于参考 ECA 实现。ECA 作者应在 `eca-example-map` 中查看当前函数调用、参数表构造、`request_id` 匹配和 UI 刷新方式；迁移到自己的项目时，仍应使用本章的迁移包，不要手工复制示例项目生成的 ECA JSON。

迁移包位于 `docs/游戏大厅系统/迁移包/`。包内只应包含：

- `script/y3/**`
- `需要合并到项目/custom/protocol/protocol.pb`
- `大厅服务ECA触发包.zip`

其中 `大厅服务ECA触发包.zip` 只供 ECA 项目使用，包含大厅服务的两个自定义事件和 26 个 ECA 函数。迁移包不包含外部项目配置器、测试 UI、测试项目玩法脚本、地图文件或项目专属配置。

## 三层配置边界

配置按下面三类处理：

| 类型 | 由谁维护 | 放在哪里 | 示例 |
| --- | --- | --- | --- |
| 框架内部固定值 | 框架维护 | `script/y3/game/lobby/**` | 玩家协议 `version` 固定为 `"2.0"`；内嵌服务协议；BOB 服务端点 |
| 项目配置 | 项目作者维护 | 编辑器“细节 > 地图设置 > 地图模式”、`match.json`、`dungeon.json`、`custom/protocol/protocol.pb` | 模式、目标关卡、最大人数、最少人数、中途加入时间 |
| 每次调用参数 | Lua 或 ECA 调用者传入 | `y3.lobby` 或 `Bind` 表 | 建立连接使用的平台地图 ID、队伍人数上限、匹配目标、分数、队伍编号、AID、聊天内容、口令 |

简单理解：

- 固定规则放在框架里，作者不用传。例如组队局内私人副本玩家数据里的 `version` 固定由框架写入 `"2.0"`。
- 项目规则在编辑器或 JSON 中配置。例如模式在编辑器的地图设置中配置，关卡、人数上限、最少人数和中途加入时间在项目 JSON 中配置。
- 每次操作必须由调用方明确提供的数据由对外调用接口传入。例如建立连接的平台地图 ID、本次创建队伍的人数上限、本次匹配的 `level_id` 和 `game_mode`。

不要把测试项目里的模式编号或关卡编号当成固定值。目标项目应在编辑器中配置自己的地图模式，并使用自己的 `match.json` 和 `dungeon.json`。

## 迁移步骤

1. 备份目标项目，以免迁移操作失误损坏项目
2. 将迁移包中的 `script/y3/` 复制到需要使用大厅服务的关卡脚本目录。
3. 将迁移包中的 `需要合并到项目/custom/protocol/protocol.pb` 合并到目标项目的 `custom/protocol/protocol.pb`。
4. 在编辑器左上角依次打开“细节 > 地图设置 > 地图模式”，按目标项目配置地图模式并保存项目。
5. 完全关闭编辑器，再按实际关卡配置 `match.json` 和 `dungeon.json`。不要在编辑器运行期间修改这两个文件；编辑器后续保存项目时会用内存中的旧值覆盖磁盘修改。
6. Lua 项目参照 `main` 分支，在地图脚本中调用 `y3.lobby.connect(平台地图ID)`；ECA 项目参照 `eca-example-map` 分支，在编辑器的触发器管理界面导入 `大厅服务ECA触发包.zip`，然后调用导入的“大厅服务 - 建立连接”函数，并将平台地图 ID 填入“玩法ID”参数。
7. 按 [验证与故障排查](./05-验证与故障排查.md) 完成本地检查和平台运行检查。

目标项目已经有 `script/y3/` 时，先备份再合并。纯 ECA 项目如果没有初始化过 `y3-lualib`，可以直接复制迁移包中的 `script/y3/`。

## 启动脚本

Lua 入口只需要加载 `y3`，然后在玩家进入大厅后建立连接：

```lua
local y3 = require 'y3'

y3.game:event('玩家-加入游戏', function (_, player)
    local result = y3.lobby.connect(190356)
    if not result.accepted then
        print('大厅服务连接请求未发出：' .. tostring(result.reason))
    end
end)
```

`y3.lobby.connect(平台地图ID)` 需要传入地图上传到平台后获得的正整数地图编号。上例 `190356` 是当前示例项目的平台地图 ID；迁移到自己的项目时，必须换成目标地图上传平台后获得的真实编号。不要使用 `GameAPI.get_dungeon_info().game_play_id` 返回的运行时值代替。

平台地图 ID 的获取方式：地图上传后，在平台后台查看该地图对应的数字 ID；无法查看时向平台运营确认。Lua 作者把该数字传给 `y3.lobby.connect(...)`，ECA 作者把它填入“大厅服务 - 建立连接”的“玩法ID”整数参数。这里的“玩法ID”只是现有 ECA 参数名，实际填写的就是平台地图 ID。它不是地图模式配置项，也不写在 `match.json` 或 `dungeon.json` 中。

`connect(平台地图ID, 是否在游戏关卡)` 是建立连接和重新建立连接的唯一入口。第二个参数可选，默认为 `false`；在目标游戏关卡内建立连接时传 `true`。组队、匹配、聊天、高级查询和有队伍的局内私人副本接口需要先连接；无队伍的局内私人副本、加入口令、获取口令、返回大厅和退出游戏不要求预先连接。

## 配置地图模式

地图模式不需要手动修改 `gamemode.json`。在编辑器左上角依次打开“细节 > 地图设置 > 地图模式”，添加大厅、匹配玩法和目标关卡实际使用的模式，并设置目标项目自己的模式编号和名称。

后续配置 `match.json` 和 `dungeon.json` 时，应填写这里配置的模式编号。模式有调整时也应回到该编辑器入口修改，不要直接编辑 `gamemode.json`。

## 配置 `match.json`

> **必须先完全关闭编辑器，再修改 `match.json`。** 编辑器运行期间仍持有旧配置；即使外部修改文件成功，之后在编辑器中保存项目也会用内存中的旧值覆盖修改。完成配置并确认文件已经保存后，再重新打开编辑器。

项目根目录下的 `match.json` 配置“哪些玩家进入同一个匹配目标、成功后进入哪个关卡和模式、各阵营目标人数、匹配分范围如何随等待时间放宽、最少多少真人可以开局，以及等待多久后允许机器人补位”。目标项目已有匹配规则时，追加或调整需要接入大厅服务的规则，不能直接覆盖整个文件。

配置前先准备两个值：

- `MATCH_MODE_ID`：在编辑器“细节 > 地图设置 > 地图模式”中查看目标玩法的模式编号。
- `MATCH_LEVEL_ID`：匹配成功后要进入的目标关卡 ID，也就是 `dungeon.json` 使用的关卡配置键。源码项目中可查看目标关卡目录下 `header.map` 的 `id`；发布或导出目录中，也可用该关卡的主 `.gmp` 文件名去掉 `.gmp` 后缀进行核对。例如 `header.map` 中的 `id` 为 `50377054694119407947881484918402159964`，这里就填写字符串 `"50377054694119407947881484918402159964"`。不要使用名称带 `trigger` 的 `.gmp` 文件。

下面示例表示：匹配模式为 `MATCH_MODE_ID`，成功后进入 `MATCH_LEVEL_ID`；目标为一个容量为 2 人的阵营；匹配分不高于 `6900` 时，凑齐 2 名真人立即开局；仍未凑齐时，等待达到 10 秒后以当前真人开局并用机器人补满空位。

```json
[
  {
    "game_mode": "MATCH_MODE_ID",
    "level_id": "MATCH_LEVEL_ID",
    "teams": [2],
    "diffuse_time": [10],
    "bot_fill_time": 10,
    "sections": [
      { "min_player_num": 2, "max_score": 6900 }
    ]
  }
]
```

| 字段 | 格式 | 含义 | 如何配置 |
| --- | --- | --- | --- |
| 根节点 | 数组 | 每一项是一条独立的匹配规则 | 一个目标关卡和模式通常对应一项；项目原有其他规则要保留 |
| `game_mode` | 整数或数字字符串 | 本条规则使用的游戏模式 | 填编辑器“地图模式”中的模式编号；还必须在目标关卡的 `dungeon.json.game_modes` 中存在 |
| `level_id` | 字符串 | 匹配成功后平台加载的目标关卡 ID | 填目标关卡 `header.map` 中的 `id`；发布或导出目录中可用主 `.gmp` 文件名核对。该值必须同时作为 `dungeon.json` 的顶层键 |
| `teams` | 由正整数组成的非空数组 | 各阵营的容量，所有元素之和是目标总人数 | `[8]` 表示一个 8 人阵营；`[4, 4]` 表示两个各 4 人的阵营；`[1, 1]` 表示两个各 1 人的阵营 |
| `diffuse_time` | 严格递增的非负整数数组，单位为秒 | 等待过程中逐档放宽可匹配的分数段范围 | 等待时间严格超过一个时间点后，才多允许跨越一个相邻分数段；严格超过最后一个时间点后不再限制分数段。它主要控制分数段扩散，不等同于机器人补位时间 |
| `bot_fill_time` | 非负整数，单位为秒 | 等待达到指定时间后，允许以当前真人开局并由机器人补满各阵营空位 | 填正数时独立控制机器人兜底时间；省略或填 `0` 时，改为在 `diffuse_time` 进入最终扩散阶段后允许机器人补位 |
| `sections` | 非空对象数组 | 匹配分区间，以及各区间允许开局的最少真人数 | 必须按 `max_score` 从低到高配置；最后一项同时作为超过所有已配置上限时的兜底分段 |
| `sections[].max_score` | 整数 | 当前分段包含的匹配分上限 | 例如相邻上限为 `200`、`400` 时，第二段表示 `200 < score <= 400`；边界值属于当前分段 |
| `sections[].min_player_num` | 正整数 | 候选对局落入该分段时，允许开局的最少真人总数 | 达到该人数便可立即开局，各阵营未占满的位置由机器人补齐；不能大于 `teams` 所有元素之和 |

`teams` 的每个元素代表一个阵营的容量，目标总人数是所有元素之和。`dungeon.json.max_player_num` 是目标关卡的房间总容量，不应小于这个总和。例如 `"teams": [4, 4]` 的目标总人数为 8，对应 `dungeon.json.max_player_num` 至少为 `8`。已有大厅队伍在匹配中不会被拆开，因此队伍人数不能超过最大的单阵营容量；创建大厅队伍时传入的“人数上限”也应遵守这一限制。

### 配置规则如何运行

1. 调用“开始匹配”时，平台按玩法、地图、`level_id` 和 `game_mode` 把玩家放入对应的匹配队列。不同目标关卡或模式不会混在一起。
2. 单人以个人为单位进入队列；已经组队的玩家以整支队伍为单位进入，匹配过程不会拆散已有队伍，并且只能由队长开始或取消匹配。
3. 开始匹配时传入的 `score` 是本次匹配单位的分数。单人是一个匹配单位；已有队伍整体是一个匹配单位。队伍没有显式传入 `score` 时，框架使用队内成员分数的平均值。平台先按 `sections[].max_score` 确定每个匹配单位所在的分数段，再把整个匹配单位放入能够完整容纳它的阵营，不会拆散已有队伍。
4. 初始阶段只允许相同分数段互相匹配。每严格超过 `diffuse_time` 中的一个时间点，允许跨越的分数段增加一段；等待较久的一方可以扩大双方可匹配的范围。超过最后一个时间点后不再限制分数段。
5. 候选对局凑满 `teams` 的总容量时直接开局；未满时，平台按候选中的“匹配单位”计算平均匹配分，再选择对应 `sections` 分段。真人总数达到该段的 `min_player_num` 时也会立即开局，各阵营剩余位置由机器人补齐。这里不是按真人数加权平均：一个多人队伍和一个单人各算一个匹配单位。
6. 如果 `bot_fill_time` 为正数，候选中等待最久的匹配单位达到该秒数后，即使真人数还没有达到 `min_player_num`，也允许用机器人补满开局。如果没有配置正数 `bot_fill_time`，则在超过 `diffuse_time` 的最后一个时间点、进入最终扩散阶段后启用这项兜底。

因此，`diffuse_time` 控制“哪些分数段可以互相凑人”，`min_player_num` 控制“正常情况下当前候选有多少真人即可开局”，`bot_fill_time` 控制“最迟等待多久后允许机器人兜底”。三者相互配合，但不按下标一一对应。

调用“开始匹配”时传入的 `level_id` 和 `game_mode` 必须与某条 `match.json` 规则完全对应，`score` 可选。例如：

```lua
y3.lobby.start_match({
    level_id = 'MATCH_LEVEL_ID',
    game_mode = 'MATCH_MODE_ID',
    score = 1000,
})
```

如果同一关卡有多个模式，为每个需要匹配的模式分别添加规则；如果同一模式会进入不同关卡，也应分别添加规则。

### 推荐配置模板

下面是一份便于迁移后调整的 8 人模板。它把目标人数、最低真人数和最长等待时间分开表达，适合先按预期效果确定数值，再写入目标项目：

```json
[
  {
    "game_mode": "MATCH_MODE_ID",
    "level_id": "MATCH_LEVEL_ID",
    "teams": [8],
    "diffuse_time": [10, 30, 60],
    "bot_fill_time": 60,
    "sections": [
      { "max_score": 1000,   "min_player_num": 4 },
      { "max_score": 3000,   "min_player_num": 6 },
      { "max_score": 6900,   "min_player_num": 8 }
    ]
  }
]
```

这份模板产生的具体效果如下：

- 候选对局按匹配单位计算的平均分不高于 `1000` 时，达到 4 名真人即可开局，并补 4 个机器人。
- 匹配单位平均分高于 `1000`、不高于 `3000` 时，达到 6 名真人即可开局，并补 2 个机器人。
- 匹配单位平均分高于 `3000` 时，正常需要凑满 8 名真人。超过示例中的最高分 `6900` 时，仍使用最后一段的 8 人规则。
- 候选中等待最久的匹配单位达到 60 秒后，无论是否达到当前分段的 `min_player_num`，都会以现有真人开局并用机器人补满。

| 等待时间 | 可匹配的分数段范围 | 未凑满 8 人时的规则 |
| --- | --- | --- |
| 不超过 10 秒 | 只匹配同一分数段 | 达到匹配单位平均分对应的 `min_player_num` 即开局并补机器人 |
| 超过 10 秒、不超过 30 秒 | 最多跨 1 个相邻分数段 | 仍按 `min_player_num` 判断是否开局 |
| 超过 30 秒、不超过 60 秒 | 最多跨 2 个相邻分数段 | 仍按 `min_player_num` 判断是否开局 |
| 达到 60 秒 | 仍按当前扩散等级组合；严格超过 60 秒后不再限制分数段 | `bot_fill_time` 已到达，不再要求达到 `min_player_num`，以当前真人开局并补机器人 |

`diffuse_time` 采用“严格超过”规则，例如等待时间恰好为 10 秒时仍处于第一行，超过 10 秒后才扩散一档；`bot_fill_time` 在达到设定秒数时生效。`sections[].min_player_num` 越小，真人不足时越容易在兜底时间之前提前用机器人补位开局。

### 必须凑满真人才开局

如果要求必须匹配到 8 名真人才开局，人数不足时持续等待，不使用机器人补位，可以配置为：

```json
[
  {
    "game_mode": "MATCH_MODE_ID",
    "level_id": "MATCH_LEVEL_ID",
    "teams": [8],
    "diffuse_time": [2147483647],
    "bot_fill_time": 0,
    "sections": [
      { "max_score": 2147483647, "min_player_num": 8 }
    ]
  }
]
```

这份配置的效果如下：

- `teams: [8]` 将目标总人数设为 8。
- 所有候选对局都要求 `min_player_num: 8`，因此不足 8 名真人时不会按最低人数规则提前开局。
- 只配置一个分数段，所有匹配分都会落入这一段，不会因为分数不同而无法互相凑人。
- `bot_fill_time: 0` 表示不使用独立的机器人补位时间，改由 `diffuse_time` 的最终扩散阶段控制机器人兜底。
- `diffuse_time` 使用 `int32` 可配置的最大值 `2147483647` 秒，约为 68 年。实际运行中不会到达最终扩散阶段，因此不会触发“以当前真人开局并补机器人”。

只把 `min_player_num` 设置为 `8` 并不够：正数 `bot_fill_time` 到时后，或未配置正数 `bot_fill_time` 但进入最终扩散阶段后，平台仍会忽略最低真人数并补机器人。也不要配置空数组 `"diffuse_time": []`，空数组会被视为已经进入最终扩散阶段，可能立即少人开局。这种配置是利用极大扩散时间实现的实际无限等待；当前配置没有单独的“永久禁止机器人补位”开关。

```json
      { "max_score": 5700, "min_player_num": 8 },
      { "max_score": 6000, "min_player_num": 8 },
      { "max_score": 6300, "min_player_num": 8 },
      { "max_score": 6600, "min_player_num": 8 },
      { "max_score": 6900, "min_player_num": 8 }
    ]
  }
]
```

这条规则的确定含义如下：

- 匹配成功后进入关卡 `317422171399597340488708779104471834431`，使用模式 `1002`。
- `teams: [8]` 表示一个容量为 8 人的阵营，目标总人数为 8。对应 `dungeon.json` 中模式 `1002` 的 `max_player_num` 也是 `8`。
- `diffuse_time` 有 30 个时间点。等待超过 2 秒可跨 1 个相邻分数段，超过 4 秒可跨 2 段，之后每严格超过一个时间点再多跨一段；超过 93 秒进入最终阶段，不再限制分数段。
- `bot_fill_time: 0` 表示没有独立的机器人补位时间，因此本例在超过 93 秒、进入最终扩散阶段后允许以当前真人开局并补机器人。
- `sections` 同时定义分数区间和各区间的最低真人开局人数。候选对局由多个单人或已有队伍组成时，平台按匹配单位的平均分确定开局人数规则；一个已有队伍整体只算一个匹配单位。

27 条 `sections` 可以按相同的 `min_player_num` 合并理解为：

| 候选对局的匹配单位平均分 | 最少真人玩家数 | 达标后的具体效果 |
| --- | --- | --- |
| 不高于 `200` | `1` | 1 名真人即可立即开局，剩余 7 个位置补机器人 |
| 高于 `200`、不高于 `600` | `4` | 凑到 4 名真人即可开局，剩余 4 个位置补机器人 |
| 高于 `600`、不高于 `1200` | `6` | 凑到 6 名真人即可开局，剩余 2 个位置补机器人 |
| 高于 `1200` | `8` | 进入最终扩散阶段前需要凑满 8 名真人；超过 93 秒后仍可少人开局并补机器人 |

例如，当前候选由匹配分 `180`、`350`、`590` 的三个单人组成，候选平均匹配分约为 `373`，应用 `max_score = 400` 的规则，需要至少 4 名真人，因此此时继续等待。再加入一名相容玩家达到 4 名真人后即可开局，其余 4 个位置补机器人。边界值包含在当前分段中，例如平均匹配分恰好为 `600` 时仍应用 `max_score = 600`。

超过最后一个 `max_score` 的匹配分会使用最后一条 `sections` 规则。本例最后一条的 `min_player_num` 为 `8`，因此在严格超过 93 秒、进入最终扩散阶段前仍要求 8 名真人。

迁移复杂规则时，先确定各阵营人数和所有可能的分数范围，再配置 `teams`、`sections`，然后配置递增的 `diffuse_time` 和机器人兜底用的 `bot_fill_time`。修改后至少验证低、中、高三个分段、已有队伍能否完整放入阵营，以及扩散和机器人补位两个时间点是否按预期生效。

## 配置 `dungeon.json`

> **必须先完全关闭编辑器，再修改 `dungeon.json`。** 编辑器运行期间仍持有旧配置；即使外部修改文件成功，之后在编辑器中保存项目也会用内存中的旧值覆盖修改。完成配置并确认文件已经保存后，再重新打开编辑器。

项目根目录下的 `dungeon.json` 配置“一个关卡支持哪些模式，以及每个模式允许怎样进入、最多容纳多少人、开局后多久内允许补人”。它的层级是“关卡 ID -> `game_modes` -> 模式 ID -> 模式配置”。

`MATCH_LEVEL_ID` 和 `MATCH_MODE_ID` 的来源与 `match.json` 相同。JSON 对象的键只能是字符串，因此这里的关卡 ID 和模式 ID 都要写在双引号中。

下面示例表示：关卡 `MATCH_LEVEL_ID` 支持模式 `MATCH_MODE_ID`；不开放公开进入，允许私人副本或口令进入；房间最多 8 人；开局后的 120 秒内允许中途加入。

```json
{
  "MATCH_LEVEL_ID": {
    "game_modes": {
      "MATCH_MODE_ID": {
        "enable_public": 0,
        "enable_private": 1,
        "max_player_num": 8,
        "can_add_in_time": 120
      }
    }
  }
}
```

| 字段 | 格式 | 含义 | 如何配置 |
| --- | --- | --- | --- |
| 顶层键 | 字符串 | 关卡 ID | 填该关卡 `header.map` 中的 `id`；发布或导出目录中可用主 `.gmp` 文件名核对。用于匹配时必须等于 `match.json.level_id` |
| `game_modes` | 对象 | 当前关卡支持的模式集合 | 每个键填一个编辑器“地图模式”中已存在的模式编号；一个关卡支持多个模式时，在这里并列添加 |
| `enable_public` | `0` 或 `1` | 是否允许通过平台公开入口进入该关卡和模式 | 需要平台公开入口时填 `1`；只允许大厅服务匹配、私人副本或口令等指定方式进入时可填 `0`。该字段不等同于是否允许调用大厅服务的“开始匹配” |
| `enable_private` | `0` 或 `1` | 是否允许私人方式进入该关卡和模式 | 使用“局内私人副本”或“加入口令”时必须填 `1`；完全禁止私人进入时填 `0` |
| `max_player_num` | 正整数 | 该关卡和模式的房间总容量 | 按玩法实际最大玩家数填写。创建私人副本或返回大厅时传入的 `max_player` 不应超过此值 |
| `can_add_in_time` | 非负整数，单位为秒 | 关卡开始后允许玩家中途加入的时间窗 | 例如 `120` 表示开始后 120 秒内可补人；填 `0` 表示不预留中途加入时间。实际能否加入还受房间容量、口令有效性和平台状态限制 |

常见组合：

| 使用场景 | `enable_public` | `enable_private` | 说明 |
| --- | --- | --- | --- |
| 只允许公开进入 | `1` | `0` | 不使用局内私人副本和口令加入 |
| 只允许私人副本或口令进入 | `0` | `1` | 大厅系统的私人副本常用配置 |
| 两种方式都允许 | `1` | `1` | 同一模式同时开放公开和私人入口 |
| 两种方式都禁止 | `0` | `0` | 该模式无法通过这两类入口进入，通常不应作为大厅目标 |

配置后检查：

1. 修改 `match.json` 和 `dungeon.json` 时编辑器已经完全关闭；修改后重新读取磁盘文件，确认内容没有被旧值覆盖。
2. `match.json[*].game_mode` 已在编辑器的“细节 > 地图设置 > 地图模式”中配置。
3. `match.json[*].level_id` 存在于 `dungeon.json` 顶层。
4. 同一条匹配规则的 `game_mode` 存在于 `dungeon.json.<关卡ID>.game_modes` 下。
5. `level_id` 使用目标关卡自身的关卡 ID，而不是平台地图 ID、地图版本 UUID、目录名或模式编号；源码项目以目标关卡 `header.map.id` 为准，主 `.gmp` 文件名只用于发布或导出目录中的核对。
6. 使用局内私人副本或加入口令时，目标模式的 `enable_private` 为 `1`，调用参数 `max_player` 不超过 `max_player_num`，加入发生在 `can_add_in_time` 时间窗内且房间未满。

三个容易混淆的 ID 对照如下：

| 名称 | 从哪里取得 | 填在哪里 |
| --- | --- | --- |
| 平台地图 ID（接口字段 `game_play_id`） | 地图上传后的平台后台 | `y3.lobby.connect(平台地图ID)`；ECA 中填入“玩法ID”参数；不写入这两个 JSON |
| 关卡 ID（`level_id`） | 目标关卡 `header.map` 中的 `id`；发布或导出目录可用主 `.gmp` 文件名核对 | `match.json.level_id`、`dungeon.json` 顶层键，以及开始匹配等接口参数 |
| 模式 ID（`game_mode`） | 编辑器“细节 > 地图设置 > 地图模式” | `match.json.game_mode`、`dungeon.json.<关卡ID>.game_modes` 的键，以及开始匹配等接口参数 |

`setting.json` 没有大厅服务框架要求直接覆盖的字段。

局内私人副本参数表不要求调用者提供底层分流方式。无队伍或一人队伍时框架按单人引擎请求提交；多人队伍时框架按 `team_info.members` 全量传递成员，不依据 `in_game` 或展示状态过滤。旧“同房分流”和“跨房合流”Lua/ECA 正式接口已删除；不要在新项目中继续创建这两个 ECA 函数或示例触发器。

## 协议与连接阶段

`script/y3/game/lobby/proto/service_pb.lua` 是线上运行时使用的内嵌服务协议，随框架复制，不需要项目作者维护。`service.pb` 仅是框架内的协议生成源，平台未将 `.pb` 打包到 `virtual_script` 时也不影响连接。

`custom/protocol/protocol.pb` 属于项目资源。目标项目没有同名文件时可以复制；已有同名文件时不能直接覆盖，应由协议维护方合并后重新生成。

加载 `script/y3` 时，框架只注册 Lua 与 ECA 对外调用接口，不创建 BOB 客户端、不加载协议、不创建网络对象。只有调用 `connect(平台地图ID, 是否在游戏关卡, 服务环境)` 时，框架才加载内嵌服务协议和项目 `protocol.pb`。本地调试固定连接 `qa`；外部项目在线上发布时应通过第三个参数显式连接 `prod`。

连接时使用的平台地图 ID 是必填调用参数。Lua 调用 `y3.lobby.connect(平台地图ID, 是否在游戏关卡, 服务环境)`；本地调试可以省略第三个参数，线上发布时传入 `prod`。ECA 调用“大厅服务 - 建立连接”时，将平台地图 ID 填入现有的“玩法ID”参数，并可选传入“是否在游戏关卡”；本地运行会连接 `qa`，线上正式环境会连接 `prod`。平台地图 ID 缺失、不是整数或小于等于 0 时，接口会立即返回 `invalid_game_play_id`。

平台地图 ID 应填写目标地图上传后获得的值。当前示例项目使用 `190356`，只能作为示例；迁移到其他项目时不要照抄。

## ECA 触发包

ECA 项目不需要手工创建完成事件，也不需要照着文档逐个编写函数。迁移包中的 `大厅服务ECA触发包.zip` 是从编辑器导出的正式触发包，包含：

- 自定义事件 `大厅服务请求完成`，参数 `回调数据` 的类型为字典（表格）；
- 自定义事件 `大厅服务状态变化`，参数 `事件数据` 的类型为字典（表格）；
- 26 个名称以“大厅服务 - ”开头的 ECA 函数。

在目标项目中打开需要使用大厅服务的主关卡，进入编辑器的触发器管理界面，使用“导入”功能选择 `大厅服务ECA触发包.zip`。压缩包应直接导入，不要解压后逐个复制其中的 JSON 文件。若编辑器提示同名事件或函数冲突，先检查目标项目是否已经导入过旧版大厅服务触发包；确认旧内容不再被项目使用后再处理冲突，不要同时保留两套同名函数。

导入完成后，检查自定义事件列表中存在 `大厅服务请求完成` 和 `大厅服务状态变化`，并检查函数列表中存在“大厅服务 - 建立连接”等 26 个函数。函数和事件通过触发包整体迁移，不需要手工复制、填写或修改内部编号。

`eca-example-map` 的正式玩家 UI 只调用 21 个函数，并不表示触发包少了 5 个函数。该示例把建连放在最小 Lua 启动代码中，同时不在玩家界面暴露设置分数和三项高级查询；目标项目仍会导入完整 26 个函数，可按需要在自己的 ECA 初始化或管理触发器中使用。

示例分支中的 `EcaLobbyExample.json`、`EcaDungeonExample.json`、30 个 `ECA*UI - ...` 触发器和 `tools/eca/` 是实现参考，不在迁移包中。不要把这些项目专属文件当成触发包内容，也不要绕过编辑器导入直接复制生成 JSON。

## ECA 调用方式

先完成 `script/y3` 的复制和触发包导入。编辑器加载 `script/y3` 后会注册对应的 `Bind` 对外调用接口，导入的 ECA 函数已经封装了调用逻辑；在触发器中直接选择“大厅服务 - 建立连接”“大厅服务 - 创建队伍”“大厅服务 - 开始匹配”等函数，并按函数参数提示填写即可，不需要添加“执行 Lua 代码”。

建立连接时必须填写目标地图上传后获得的平台地图 ID；在目标游戏关卡中调用时，将“是否在游戏关卡”设为 `true`。开始匹配时填写的 `level_id` 和 `game_mode` 必须与本章前面配置的 `match.json`、`dungeon.json` 以及编辑器地图模式一致。

异步函数被受理后，最终结果仍通过 `大厅服务请求完成` 事件的 `回调数据` 返回。触发器应保存函数立即返回的 `request_id`，并在事件中按同一 `request_id` 匹配结果；具体字段和完整流程见 [ECA 功能使用](./04-ECA功能使用.md)。

迁移完成后，按项目使用方式阅读 [Lua 功能使用](./03-Lua功能使用.md) 或 [ECA 功能使用](./04-ECA功能使用.md)。
